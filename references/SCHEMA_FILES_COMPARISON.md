## Summary

- **`philgeps-schema.md`** is the richest **schema evolution** narrative (why columns changed, file paths, XLSX quirks).
- **`PHILGEPS_SCHEMA_ANALYSIS.md` / `.json`** are a matched pair for **which columns exist in each schema period** — same facts, human vs machine format.
- **`PHILGEPS_CANONICAL_FIELD_MAP.json`** is the primary **programmatic mapping** artifact: canonical field names used by the parent pipeline, with every source column name for S1–S5.
- **`PHILGEPS_OCDS_CSV_CROSSWALK.md`** is the **human-readable join** across OCDS, PhilGEPS live-system fields, CSV exports, and canonical names.
- Schema analysis JSON **feeds** the canonical field map builder; pipeline config at repo root (`config/schema_mappings.yaml`) is the **executable source of truth** that the JSON mirrors.

## 1. `philgeps-schema.md` vs `PHILGEPS_SCHEMA_ANALYSIS.md`

Both describe the same 5 schemas and 14 semantic categories, but they differ significantly in depth.

### What's ONLY in `philgeps-schema.md`

This file contains substantial narrative and contextual material absent from the condensed version:

- **Executive Summary** with purpose statement
- **Schema Evolution Timeline** — a dedicated section per schema covering:
  - Real file names and folder paths (e.g. `2000-01 -- 2000-12.xlsx`, `RAW/raw/2013-2020/`)
  - The XLSX header-at-row-3 quirk and metadata rows
  - Narrative on *why* changes happened (data standardization, format change, privacy law, PhilGEPS 2.0 migration)
  - Code snippets, e.g. the Python `UOM` handling example
- **Per-schema characteristics** (column-by-column callouts like "Column 1: Organization Name (not Procuring Entity)")
- **Missing Features** lists per schema
- **Schema 5 deep dive** — why the V2 export exists, evidence it's the same as Schema 4, and a pros/cons comparison vs Schema 3
- **Category Breakdown by Schema Period** — 14 separate tables (one per semantic group) with `Evolution:` commentary under each
- **Field Category Summary** table with star-rated stability (⭐ / ⭐⭐ / ⭐⭐⭐) and field counts per category
- **Key Observations & Insights** — 6 numbered findings (Location Data Gap, Privacy Considerations, Status Canonicalization, Column Order Unreliability, Typo Correction, File Naming Conventions)
- **Document version, last updated, next review** metadata

### What's ONLY in `PHILGEPS_SCHEMA_ANALYSIS.md`

- A **source link** to `Schema.tsx` at the top
- A consolidated **single semantic grouping table** (the detailed file splits categories across 14 tables; this file keeps them as a clean sequence of similarly-styled tables)
- A condensed 5-bullet **Key Observations** section (vs the 6 numbered insights in the detailed file)

### Content discrepancies between the two MD files

The two files agree on schema structure (column counts, field names, schema periods) but there are a few wording-level differences worth noting:

| Topic | `philgeps-schema.md` | `PHILGEPS_SCHEMA_ANALYSIS.md` |
|-------|----------------------|-------------------------------|
| Quick Reference table | Uses `**Schema 1**` (bold) formatting in the schema column | Plain text |
| Column 37 (Schema 3) | Marked with ⚠️ typo flag | Marked with ⚠️ typo flag — **also adds the flag to Schema 3**, which the detailed file omits in its column-comparison table (though it acknowledges the typo in narrative) |
| Category order in semantic grouping | Procuring Entity → Bid ID → Bid Timeline → Budget → Procurement → Line Items → UNSPSC → Bid Status → Award ID → Award Timeline → Contract → Award Status → Awardee Info → Competition | Procuring Entity → Bid ID → **Budget → Bid Timeline** → Procurement → Line Items → UNSPSC → Bid Status → Award ID → Award Timeline → Contract → Award Status → Awardee Info → Competition (Budget and Bid Timeline are swapped) |
| Quick Reference "Key Change" column | Same wording | Same wording |
| Insights section | 6 findings, including "File Naming Conventions" | 5 findings, omits file naming |

The factual schema data (column counts, renames, additions, removals) is **identical** between the two files.

## 2. `PHILGEPS_SCHEMA_ANALYSIS.md` vs `PHILGEPS_SCHEMA_ANALYSIS.json`

These two files are **intentional counterparts** — same source, same content, two formats. The JSON is a structured representation of the markdown.

### Structure mapping

| Markdown section | JSON key |
|------------------|----------|
| Title (H1) | `title` |
| Source link | `source` |
| Analysis Date | `analysis_date` (ISO format: `2025-11-14`) |
| Purpose | `purpose` |
| Intro paragraph | `summary` |
| Quick Reference table | `quick_reference` (array of objects) |
| Semantic Grouping tables | `semantic_grouping` (array of `{category, fields[]}`) |
| Side-by-Side Comparison table | `side_by_side_comparison` (object with `legend` and `rows`) |
| Key Observations bullets | `key_observations` (array of strings) |

### Format conventions in the JSON

- **Em-dashes** (`—`) in the markdown are converted to `null` in the JSON. The string `"REMOVED"` is kept as a literal string (not null), distinguishing "field removed" from "field never existed".
- The markdown's emoji flags (⭐ metadata, 🌍 location, ⚠️ typo) are normalized into a `flags` array per cell, e.g. `["major", "location"]` or `["typo"]` / `["fixed_typo"]`. The legend maps:
  - ⭐ → `metadata`
  - 🌍 → `location`
  - **Bold** → `major`
- Cells without special flags simply omit the `flags` key.
- The JSON adds a `"position"` integer to each row in the side-by-side comparison (1–46), which the markdown expresses as the leftmost `#` column.

### Content fidelity

The two are **content-identical**. No data is added, removed, or changed in the round-trip between formats — the JSON is a faithful, machine-readable serialization of the markdown.

## 3. Which schema-evolution file should you use?

| Use case | Recommended file |
|----------|------------------|
| Understanding *why* the schema changed, with historical context and file paths | `philgeps-schema.md` |
| Onboarding someone quickly with just the tables | `PHILGEPS_SCHEMA_ANALYSIS.md` |
| Positional column comparison across S1–S5 | `PHILGEPS_SCHEMA_ANALYSIS.json` → `side_by_side_comparison.rows` |
| Semantic field renames (e.g. `Organization Name` → `Procuring Entity (PE)`) | `PHILGEPS_SCHEMA_ANALYSIS.json` → `semantic_grouping` |
| Cross-referencing the original source | `PHILGEPS_SCHEMA_ANALYSIS.md` / `.json` (they cite GitHub `Schema.tsx`) |
| Authoritative detail on real raw files | `philgeps-schema.md` |

## 4. `PHILGEPS_CANONICAL_FIELD_MAP.json` vs `PHILGEPS_OCDS_CSV_CROSSWALK.md`

These are **complementary**, not duplicates.

| Aspect | `PHILGEPS_CANONICAL_FIELD_MAP.json` | `PHILGEPS_OCDS_CSV_CROSSWALK.md` |
|--------|--------------------------------------|----------------------------------|
| Primary key | `canonical_field` (53 fields) | `ocds_field` (151 rows, incl. unmapped) |
| Schema coverage | S1–S5 source column per canonical field | S1–S5 in **Canonical** column; V1/V2 CSV columns for quick CSV lookup |
| PhilGEPS 1.5 / 2.0 | Via `ocds_paths` + crosswalk embed | Explicit columns per row |
| Best for | ETL, normalizers, API codegen | Analysts, OCDS implementers, gap analysis |
| Regenerated | Yes — `python scripts/build_schema_field_map.py` | Canonical column auto-updated; OCDS/1.5/2.0 columns are curated |

### JSON top-level keys

| Key | Contents |
|-----|----------|
| `metadata` | Generation timestamp, source file paths |
| `schemas` | S1–S5 labels, periods, formats, column counts |
| `semantic_grouping` | Copy of `PHILGEPS_SCHEMA_ANALYSIS.json` semantic groups |
| `canonical_fields[]` | Per-field: `source_columns`, `ocds_paths`, `category`, `canonical_ai` string |
| `source_column_index` | Per schema: `{Source Column: canonical_field}` — same as `config/schema_mappings.yaml` |
| `ocds_crosswalk[]` | Machine-readable copy of the markdown crosswalk rows |

### Compact schema keys (Canonical column)

| Key | Schema | Period |
|-----|--------|--------|
| S1 | Schema 1 | 2000–2015 XLSX |
| S2 | Schema 2 | 2016–2020 XLSX |
| S3 | Schema 3 | 2021–2024 CSV (V1) |
| S4 | Schema 4 | 2025 CSV (V2 layout) |
| S5 | Schema 5 | 2021–2024-V2 CSV |

## 5. Which mapping file should you use?

| Use case | Recommended file |
|----------|------------------|
| Build a column normalizer for all years 2000–2025 | `PHILGEPS_CANONICAL_FIELD_MAP.json` → `source_column_index` |
| Look up one canonical field’s names in every schema | `PHILGEPS_CANONICAL_FIELD_MAP.json` → `canonical_fields[].source_columns` |
| Trace OCDS path → CSV column → canonical field | `PHILGEPS_OCDS_CSV_CROSSWALK.md` or `ocds_crosswalk[]` in JSON |
| PS-DBM official live-system field names | `philgeps-1.5.json`, `mphilgeps.json` |
| Full OCDS 1.1.5 field tree | `ocds_reference.json` |
| **Run** the ingest pipeline | `config/schema_mappings.yaml` in this repo (JSON is derived documentation) |

## 6. Maintenance

When `config/schema_mappings.yaml` or `references/PHILGEPS_SCHEMA_ANALYSIS.json` changes:

```bash
pip install -r requirements.txt
python scripts/build_schema_field_map.py
```

This refreshes `PHILGEPS_CANONICAL_FIELD_MAP.json` and the **Canonical** column in `PHILGEPS_OCDS_CSV_CROSSWALK.md`. Curated columns (OCDS, PhilGEPS 1.5/2.0, V1/V2 CSV) are preserved unless the script source data changes.

## Key Takeaways

1. **`philgeps-schema.md` is the richest schema-evolution narrative** — context the JSON lacks.
2. **`PHILGEPS_SCHEMA_ANALYSIS.md` and `.json` are a matched pair** for column layout facts across S1–S5.
3. **`PHILGEPS_CANONICAL_FIELD_MAP.json` is the programmatic hub** — use it for code; regenerate it when pipeline config changes.
4. **`PHILGEPS_OCDS_CSV_CROSSWALK.md` is the human OCDS join view** — best for tracing gaps between open CSV and live PhilGEPS 2.0.
5. **The three schema docs and the mapping JSON agree on facts** (5 schemas, 40→43→46 columns); differences are presentation layer, not conflicting data.
6. **Minor structural differences** exist between the two schema markdown files (category ordering, typo flags in comparison table), but none affect canonical mapping correctness.
